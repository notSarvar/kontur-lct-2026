## Файлы на сервере

- `/opt/kontur/releases/<release>/` — исходники и конфигурация конкретного выпуска.
- `/opt/kontur/current` — ссылка на текущий выпуск.
- `/opt/kontur/workspace` — общая рабочая копия Git для команды; чтение и запись разрешены всем локальным пользователям.
- `/opt/kontur/production.env` — параметры размещения, вне Git.
- `/opt/kontur/data/state.json` — постоянное состояние; пересоздание контейнера его сохраняет.
- `/opt/kontur/backups/` — ежедневные сжатые снимки состояния, хранящиеся 14 дней.
- `/etc/systemd/system/kontur-backup.{service,timer}` — ежедневный запуск резервного копирования. Копии находятся на том же диске и не защищают от потери всей ВМ.

## Доступ команды

Репозиторий публичный: https://github.com/notSarvar/kontur-lct-2026. Скачать код можно без учётной записи; для отправки изменений нужны права участника репозитория и собственная авторизация GitHub.

После входа по личной SSH-учётной записи общая рабочая копия находится здесь:

```sh
cd /opt/kontur/workspace
git config --global --add safe.directory /opt/kontur/workspace
git status
```

ACL рабочей копии разрешают всем локальным пользователям читать и редактировать файлы; новые файлы и каталоги наследуют общий доступ. Для параллельных изменений удобнее собственная копия в домашнем каталоге и отдельная ветка:

```sh
git clone https://github.com/notSarvar/kontur-lct-2026.git ~/kontur
cd ~/kontur
git switch -c feature/my-change
```

`/opt/kontur` и исходники выпусков доступны всем для просмотра. Рабочие данные, резервные копии и `production.env` сохраняют ограниченные права. Правки в `workspace` публикуются отдельным выпуском по инструкции ниже; общий доступ к исходникам не выдаёт права администратора или управление Docker. Для входа на ВМ каждому участнику нужна учётная запись с его публичным SSH-ключом.

## Проверка и управление

```sh
cd /opt/kontur/current
docker compose --env-file /opt/kontur/production.env -f deploy/compose.yaml ps
docker compose --env-file /opt/kontur/production.env -f deploy/compose.yaml logs --tail=100
curl -f http://127.0.0.1/api/health
sh deploy/backup.sh
```

Для перезапуска только приложения:

```sh
docker compose --env-file /opt/kontur/production.env -f deploy/compose.yaml restart app
```

Не запускайте второй экземпляр приложения с тем же каталогом данных. Каждый процесс держит собственное состояние и очередь изменений в памяти.

При обычном перезапуске загружается принятый план без повторной оптимизации: назначения, уведомления и разница последнего изменения сохраняются. Пересчёт при загрузке выполняется только при миграции, восстановлении недостающих координат или отсутствии актуального плана.

Проверка опубликованного сайта без применения изменений:

```sh
DEPLOY_URL=http://158.160.161.151 node scripts/check-deployment.mjs
```

Скрипт проверяет OR-Tools, SSE, график, карточку заявки, отмену предпросмотра, все разделы, редактор шагов регламента на HTTP, мобильный экран, публичный пульт `/hackathon` и неизменность дня. Требуются локальные зависимости проекта и установленный браузер Playwright.

Разделение интерфейсов по адресу не является авторизацией. Публичная версия — общая демосреда на синтетических данных: посетители могут менять план через API. Для реальных рабочих данных сначала нужна авторизация и разграничение доступа ко всем изменяющим API.

## Обновление

1. Создайте новый каталог выпуска и загрузите туда исходники. Не копируйте локальные `.data`, ключи или `.env`.
2. Сделайте резервную копию через `deploy/backup.sh`.
3. Задайте новый `RELEASE_TAG` в `/opt/kontur/production.env`, проверьте `docker compose ... config --quiet` и соберите образ командой `docker compose ... build`.
4. Запустите `docker compose ... up -d --wait`. Проверьте health, интерфейс и доступность OR-Tools через `/api/optimizers`.
5. Переключите `/opt/kontur/current` на новый выпуск. Сохраните предыдущий образ и выпуск для отката.

Для отката запустите Compose из предыдущего выпуска с его `RELEASE_TAG`. Перед восстановлением резервного `state.json` остановите приложение; не заменяйте состояние работающего процесса. При изменении формата состояния нужен совместимый снимок.

## DNS и сеть этой ВМ

На момент установки VPN-интерфейс `wg0` направлял все DNS-запросы к неработающему резолверу. Для скачивания зависимостей временно добавлялись маршруты DNS только для доменов Docker, Debian, npm и PyPI через `eth0`; после сборки исходные домены `ru-central1.internal auto.internal` восстановлены. VPN и его маршруты не отключались.

Контейнер приложения использует DNS подсети `10.130.0.2` через параметр `KONTUR_DNS`. При переносе в другую подсеть задайте её DNS. Если DNS хоста не исправлен, последующая сборка снова потребует настройки разрешения имён репозиториев.

Nginx сохраняет HTTP Host, ограничивает частоту API-запросов и передаёт SSE `/api/events` без буферизации. Для домена нужно направить A-запись на IP, настроить TLS и обновить `PRODUCT_ORIGIN`; правила облачной группы безопасности должны разрешать соответствующие порты.

Тип IP — свойство ресурса VPC. На 28 сентября у ВМ нет сервисного аккаунта в metadata, а настроенный CLI Yandex Cloud отсутствует и на сервере, и локально. Изменение через API не выполнялось. В консоли: **Virtual Private Cloud → IP-адреса → `158.160.161.151` → ⋮ → Сделать статическим → Изменить**. Преобразование сохраняет текущий адрес; переустанавливать сайт не нужно. Если адрес уже статический, дополнительного действия не требуется.
