# Замена оценочного общественного транспорта на API

Проверено 17.09.2026 по документации провайдеров. Подключение и платные запросы ещё не выполнялись: нужен доступ к выбранному API. Текущие OSM-матрицы считают пешие поездки; общественный транспорт в `prepared-travel.js` остаётся формулой расстояние/скорость + 12 минут. Это основной заменяемый компонент.

## Выбор

**Первый кандидат для проверки — Яндекс «Матрица расстояний», режим `transit`.** API также поддерживает `walking`, возвращает направленные времена в секундах и расстояния в метрах. Обычный ключ JavaScript-карты не означает доступа к этому продукту. [Запрос](https://yandex.ru/maps-api/docs/distancematrix-api/request.html), [ответ](https://yandex.ru/maps-api/docs/distancematrix-api/response.html).

Постоянного бесплатного тарифа Матрицы нет. Опубликованный стандартный тариф начинается с 20 800 ₽/месяц при лимите 1000 элементов/сутки; это не предложение покупать лицензию для хакатона. На странице тарифов описан запрос тестового доступа: создать ключ соответствующего API в кабинете и обратиться к менеджеру/поддержке, указав цель. Срок, лимит и разрешённое хранение тестовых данных нужно получить при активации; автоматические «14 дней» не обещаются. [Тариф 2026](https://yandex.ru/maps-api/docs/news/new-billing/tariffs.html), [порядок получения теста](https://yandex.ru/maps-api/tariffs).

**Альтернатива — Google Routes API / Compute Route Matrix, `TRANSIT`.** Поддерживает общественный транспорт с пешими подходами и временем отправления. Базовая квота Compute Route Matrix Essentials — 10 000 элементов/месяц; нужен включённый биллинг. В документации Cloud указана приостановка новых регистраций для пользователей в России. Не следует предполагать наличие рабочего биллинга или полноту данных для конкретных пригородных поездок — сначала проверка на примерах. [Transit](https://developers.google.com/maps/documentation/routes/transit-route), [тарифы](https://developers.google.com/maps/billing-and-pricing/pricing), [биллинг](https://developers.google.com/maps/documentation/routes/usage-and-billing), [ограничение регистрации](https://docs.cloud.google.com/billing/docs/resources/currency).

## Объём наших данных

После объединения одинаковых координат только для запросов к провайдеру (все заявки остаются отдельными):

| Участок    | Точки с офисом | Направленные пары без диагонали | Полная квадратная матрица |
| ---------- | -------------: | ------------------------------: | ------------------------: |
| Восток     |             65 |                            4160 |                      4225 |
| Юго-восток |             69 |                            4692 |                      4761 |
| Югоцентр   |             55 |                            2970 |                      3025 |
| Всего      |            189 |                           11822 |                     12011 |

Это один способ передвижения и одно время отправления. Три временных среза — минимум 35 466 попарных результатов. Прямоугольные пакетные запросы могут включать диагональ и увеличить фактический расход. Обе системы тарифицируют элементы, а не HTTP-пакеты. У синхронного Яндекса и у Google Transit предел пакета — 100 элементов. [Яндекс: лимиты](https://yandex.ru/maps-api/docs/distancematrix-api/index.html), [единица тарификации](https://yandex.ru/dev/tariffs/doc/ru/matrix/terms/index), [Google: лимиты](https://developers.google.com/maps/documentation/routes/usage-and-billing).

Начинать следует с 10–20 пар: короткий городской переезд, пересадка через метро, Москва–Домодедово, Кашира/Ступино, одинаковая точка. Сравнить обе направленности и несколько времён отправления с нынешней формулой и публичным планировщиком провайдера. Без такого измерения уменьшение погрешности в процентах не заявляется.

## Изменения в Контуре после получения доступа

1. Серверный провайдер поездок с отдельным ключом в локальном окружении, пакетами до 100 элементов, ограничением расхода и явной ошибкой при недоступности. Ключ не входит в браузер, репозиторий или журнал запросов.
2. В расчёте маршрута использовать `travel(from, to, mode, departureTime)`. Сейчас `createEvaluator` передаёт только точки и инженера. Одной статической матрицы на день недостаточно: поездка начинается после предыдущей работы и ожидания. Сначала допустимы явно обозначенные временные срезы, затем проверка выбранных переездов на фактическое плановое время с повторной проверкой окон и смен.
3. Дату транспортного расчёта выбрать отдельно от исходной даты CSV 17.08.2026. Яндекс не принимает `departure_time` в прошлом. Использовать будущий демонстрационный день с явно обозначенным соответствием; не выдавать текущие расписания за исторические.
4. Сохранять происхождение и время расчёта каждой поездки. Недоступный путь не считать нулём и не заменять формулой без отметки. Пеший вариант сравнивать с транспортным; не вызывать внешний API внутри каждой итерации ALNS.
5. Для новой заявки получать только недостающие направления и необходимые времена, затем пересчитывать и проверять кандидат плана. Существующий процесс предпросмотра сохраняется.

## Хранение и карта

Текущие условия Яндекс Матрицы допускают временный кэш до 30 дней при указанной в условиях оплаченной стандартной лицензии; расширенная лицензия допускает хранение на срок оферты. Условия тестового доступа нужно подтвердить отдельно. Поэтому ответы нельзя автоматически положить в Git рядом с OSM-данными. [Условия Яндекса](https://yandex.ru/dev/tariffs/doc/ru/matrix/terms/index).

У Google ограничено кэширование результатов; если данные Routes отображаются на карте, требуется Google Map. При выборе этого варианта нужно пересмотреть текущую Leaflet/OSM-карту и хранение результатов, а не просто подставить новый URL. [Политика Google Routes](https://developers.google.com/maps/documentation/routes/policies).
