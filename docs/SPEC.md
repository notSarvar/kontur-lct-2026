# Уточнённое ТЗ и математическая модель

Состояние на 17.09.2026: реализация подключена к синтетическим CSV; JavaScript, React, Node.js. Источники: официальный PDF «3. Билайн Бизнес», Excel «Нормативы», запись встречи. Пользователь подтвердил приоритет PDF, использование только синтетических заявок, синтетический состав инженеров, бесплатные сервисы и статус ручного согласования. Все глобальные проблемы, включая шесть строк «Информация», считаются авариями.

## 1. Данные

Три независимых участка на 17.08.2026: Восток (66), Юго-восток (83), Югоцентр (56). Бригада — один человек. Контрольные назначения не используются. Сохраняются исходный ID, порядок, типы BK/HD, адрес, район и окно. Адрес офиса извлекается отдельно. Каждая строка — визит, дубликаты адресов не объединяются.

Три навыка: локальный, подключения/дозаказы, аварийный. Длительность работы без дороги: 30, 70, 20, 80 минут соответственно. Работа и документы складываются по Excel; фиксированные 20 минут дороги заменяются оценкой переезда.

Синтетические инженеры выводятся по нагрузке каждого навыка на две смены (08–17, 14–23), с целевой занятостью 65%. Резерв на переезды при оценке штата — 20 минут на заявку. Состав доступного пула фиксируется до оптимизации и одинаков для основного и базового алгоритмов. Это бизнес-допущения, не восстановленные реальные данные. Диспетчер может добавлять людей и менять навыки, транспорт, смену и базу.

## 2. Математическая постановка

Пусть I — заявки, K — заданный состав инженеров, o_k — текущая/стартовая точка. Для заявки i известны окно начала [a_i,b_i], длительность p_i, требуемый навык q_i, срочность r_i. Для инженера k известны навыки Q_k, смена [A_k,B_k] и доступность. t^k_ij и d^k_ij — время и расстояние между точками для его способа передвижения.

Решение — упорядоченные списки R_k и неназначенный набор U. Можно записать через бинарные переменные y_ik (назначение), x_ijk (переезд), z_k (задействован), u_i (не назначен) и времена начала s_i. Полная маршрутная модель также требует баланса входящих/исходящих дуг и связности с o_k; приведённые ниже условия задают ограничения уже построенных последовательностей.

- Для каждой заявки: сумма y_ik + u_i = 1.
- Если q_i не входит в Q_k или не подходит обязательный ресурс, y_ik = 0.
- Для последовательных i,j в R_k: s_j >= s_i + p_i + t^k_ij.
- Для первого i в R_k: s_i >= max(текущее время, A_k, конец перерыва, конец зафиксированной работы) + t^k_(o_k,i).
- Для каждого назначенного i: a_i <= s_i <= b_i; s_i + p_i <= B_k.
- Возврат в офис после последнего визита не требуется.
- Выполненные визиты неизменны; начатый выезд/работа остаётся закреплённым префиксом маршрута. Обычный перерыв начинается после него.

Цель лексикографическая:

1. Число неназначенных аварий.
2. Общее число неназначенных заявок.
3. Суммарное ожидание начала аварий после max(текущего времени, поступления, начала окна).
4. Число задействованных инженеров.
5. Суммарное расстояние.
6. Число смен назначенного инженера (если включена стабильность).
7. Суммарное время переездов.

Таким образом, не используется один произвольный гигантский штраф, который может случайно обменять обязательное ограничение на экономию километров. Жёсткие ограничения всегда проверяются. Раннее выполнение аварий выше экономии персонала — выбранное допущение; PDF не задаёт численных весов этих целей.

## 3. Решатель и базовое сравнение

Самостоятельная реализация ALNS: несколько начальных решений, regret-2 по альтернативным инженерам, случайное/связанное удаление визитов, попытки освободить целый маршрут, повторная вставка. Успешные операторы выбираются чаще. У каждой вставки заново проверяются все дальнейшие времена. Возвращается лучший допустимый найденный план. Глобальная оптимальность не утверждается.

Базовый алгоритм — §2.3 PDF: заявки в исходном порядке, первый допустимый инженер во входном порядке, добавление в конец. Исторические контрольные назначения не служат эталоном. Метрики: число назначенных, число инженеров, километры по инженерам и суммарно, время дополнительно. Планы с разным набором размещённых заявок отмечаются как несопоставимые для прямой процентной экономии расстояния.

Основной источник метода: [Ropke, Pisinger, 2006](https://pubsonline.informs.org/doi/10.1287/trsc.1050.0135). Это адаптация схемы, не перенос авторского кода и не точное воспроизведение всех операторов статьи.

## 4. Ручное согласование

При конфликте окно не расширяется автоматически. Заявка получает `manual_review` — «Требует согласования», причину и запись в очереди диспетчера. Она не удаляется и не заменяется новой заявкой. Повторная оптимизация сама её из очереди не извлекает.

Диспетчер связывается с клиентом вне системы и указывает результат разговора, новое окно либо исправленные координаты. Можно закрепить конкретного инженера. Команда `job.resolve` сохраняет исходное окно, старые/новые значения и комментарий, затем повторно проверяет расписание. Невыполнимое ручное назначение снова возвращается в очередь. Проблема на объекте (`blocked`) — отдельный сценарий.

Подход соответствует полуавтоматическому планированию: система предлагает допустимые назначения, диспетчер отвечает за согласование спорных изменений. Пример описания такого разделения: [Microsoft Field Service Schedule Assistant](https://learn.microsoft.com/en-us/dynamics365/field-service/schedule-assistant).

## 5. Геоданные и транспорт

Координаты зданий подготовлены через Nominatim с кэшем, ограничением 1,1 секунды между запросами и без вызовов при обычном запуске. Нераспознанные адреса имеют пустые координаты и требуют проверки. Разные номера дома нельзя молча считать одним адресом. В двух офисах исходные суффиксы «с» не совпали с найденными «к»: приблизительные точки вынесены в `data/beeline/office-assumptions.json`, отмечены в интерфейсе, доступны для изменения.

Пешеходная модель: 1,25 × прямое расстояние / 4,8 км/ч. Общественный транспорт: 1,35 × прямое расстояние / 23 км/ч + 12 минут подхода/ожидания, с выбором ходьбы, если она быстрее. Это допущение для прототипа, разрешающего упрощённый расчёт по PDF. Реальные линии, пересадки, расписания и пробки отсутствуют. Километры также оценочные; геометрия пунктирная. Для прикладной точности нужна транспортная сеть или провайдер.

## 6. Выполненные этапы и проверка

- Изолирован импорт синтетических файлов и нормативов с сохранением происхождения.
- Состав инженеров синтезирован из требований и нагрузки.
- Ядро заменено на ALNS; базовый алгоритм приведён к PDF; SLA завершения удалён.
- Добавлены километры, число используемых инженеров, выбор участка и изменения маршрутов.
- Подключены очередь согласования, ручной исполнитель, комментарий и история.
- Код разделён на domain/application/optimization/infrastructure/http и компоненты интерфейса по функциям; добавлен Prettier.
- Проверки: инварианты на 35 сценариях, сохранение текущей работы, нормативы, исходный порядок baseline, повторный импорт, согласование, независимый полный перебор малого примера; браузерные сценарии и сборка.

Воспроизводимое сравнение на исходных участках сохраняет `npm run benchmark` в `docs/benchmark.json`. В нём явно указано число геокодированных заявок и причины неназначения. Результаты основаны на приближённом транспорте и синтетическом штате; это проверка прототипа, не доказательство экономического эффекта у Билайна.
