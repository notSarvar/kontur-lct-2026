# Уточнённое ТЗ и математическая модель

Состояние на 17.09.2026: реализация подключена к синтетическим CSV; JavaScript, React, Node.js. Источники: официальный PDF «3. Билайн Бизнес», Excel «Нормативы», запись встречи. Пользователь подтвердил приоритет PDF, использование только синтетических заявок, синтетический состав инженеров, бесплатные сервисы и статус ручного согласования. Последнее уточнение пользователя разделяет HD «Авария» и «Информация» внутри BK «Глобальная проблема»: 15 срочных аварий и 6 обычных информационных выездов.

## 1. Данные

Три независимых участка на 17.08.2026: Восток (66), Юго-восток (83), Югоцентр (56). Бригада — один человек. Контрольные назначения не используются. Сохраняются исходный ID, порядок, типы BK/HD, адрес, район и окно. Адрес офиса извлекается отдельно. Каждая строка — визит, дубликаты адресов не объединяются.

Три названные в Q&A квалификации: локальная заявка, подключение и дозаказ — раздельные навыки. Для глобальных проблем пока сохранён отдельный синтетический аварийный навык; это допущение требует подтверждения. Длительность работы без дороги: локальная 30, подключение 70, дозаказ 20, авария 80 минут. Для информации принято 30 минут как явное допущение, отдельной строки Excel нет. Работа и документы складываются по Excel; фиксированные 20 минут дороги заменяются оценкой переезда.

Синтетические инженеры выводятся по нагрузке каждого навыка на две смены (08–17, 14–23), с целевой занятостью 65%. Резерв на переезды при оценке штата — 20 минут на заявку. Состав доступного пула фиксируется до оптимизации и одинаков для основного и базового алгоритмов. Это бизнес-допущения, не восстановленные реальные данные. Диспетчер может добавлять людей и менять навыки, транспорт, смену и базу.

HD «Мониторинг» относится к BK «Локальная заявка». Для глобальных проблем принимаются только известные HD «Авария» и «Информация», неизвестное значение останавливает импорт. Ширина окна не определяет срочность: 11 аварий имеют суточное окно, четыре — двухчасовое. Окно сохраняется как в CSV. Новые ручные заявки получают явно выбранный приоритет.

На один и тот же адрес сохраняются все строки и весь объём работ. Для шести аварий на одной подтверждённой точке остаётся 6 × 80 = 480 минут работ плюс один подход, если визиты последовательны. Несколько корпусов/домов одной улицы не считаются одним объектом; между ними рассчитывается путь.

## 2. Математическая постановка

Пусть I — заявки, K — заданный состав инженеров, o_k — текущая/стартовая точка. Для заявки i известны окно начала [a_i,b_i], длительность p_i, требуемый навык q_i, срочность r_i. Для инженера k известны навыки Q_k, смена [A_k,B_k] и доступность. t^k_ij и d^k_ij — время и расстояние между точками для его способа передвижения.

Решение — упорядоченные списки R_k и неназначенный набор U. Можно записать через бинарные переменные y_ik (назначение), x_ijk (переезд), z_k (задействован), u_i (не назначен) и времена начала s_i. Полная маршрутная модель также требует баланса входящих/исходящих дуг и связности с o_k; приведённые ниже условия задают ограничения уже построенных последовательностей.

- Для каждой заявки: сумма y_ik + u_i = 1.
- Если q_i не входит в Q_k или не подходит обязательный ресурс, y_ik = 0.
- Для последовательных i,j в R_k: s_j >= s_i + p_i + t^k_ij.
- Для первого i в R_k: s_i >= max(текущее время, A_k, конец перерыва, конец зафиксированной работы) + t^k_(o_k,i).
- Для каждого назначенного i: a_i <= s_i <= b_i; s_i + p_i <= B_k.
- Возврат в офис после последнего визита не требуется.
- Выполненные визиты неизменны; начатый выезд/работа остаётся закреплённым префиксом маршрута. Обычный перерыв начинается после него.

Цель лексикографическая. Общий префикс: (число неназначенных аварий, все неназначенные). Далее выбирается политика:

- `economy`: (задействованные инженеры, суммарное ожидание аварий, смены исполнителя, километры, время в пути).
- `emergency`: (суммарное ожидание аварий, задействованные инженеры, смены исполнителя, километры, время в пути).

Для аварии ожидание `max(0, s_i - max(a_i, released_i))`: уже накопленное ожидание сохраняется при пересчёте. У исходных заявок `released_i=0`, у новой — время создания. Стабильность отключаема; при включении стоит перед километрами. Политика по умолчанию `economy`, новая срочная заявка переключает на `emergency`. Диспетчер может переключить вручную с предпросмотром.

Один произвольный большой вес не используется. Начальные решения, сравнение ALNS, вставки и regret применяют одну политику. Жёсткие ограничения не обмениваются на экономию.

## 3. Решатель и базовое сравнение

Самостоятельная реализация ALNS: несколько начальных решений, regret-2 по альтернативным инженерам, случайное/связанное удаление визитов, попытки освободить целый маршрут, повторная вставка. Успешные операторы выбираются чаще. У каждой вставки заново проверяются все дальнейшие времена. Возвращается лучший допустимый найденный план. Глобальная оптимальность не утверждается.

Базовый алгоритм — §2.3 PDF: заявки в исходном порядке, первый допустимый инженер во входном порядке, добавление в конец. Исторические контрольные назначения не служат эталоном. Метрики: число назначенных, число инженеров, километры по инженерам и суммарно, время дополнительно. Планы с разным набором размещённых заявок отмечаются как несопоставимые для прямой процентной экономии расстояния.

Основной источник метода: [Ropke, Pisinger, 2006](https://pubsonline.informs.org/doi/10.1287/trsc.1050.0135). Это адаптация схемы, не перенос авторского кода и не точное воспроизведение всех операторов статьи.

## 4. Ручное согласование

При конфликте окно не расширяется автоматически. Заявка получает `manual_review` — «Требует согласования», причину и запись в очереди диспетчера. Она не удаляется и не заменяется новой заявкой. Повторная оптимизация сама её из очереди не извлекает.

Диспетчер связывается с клиентом вне системы и указывает результат разговора, новое окно либо исправленные координаты. Можно закрепить конкретного инженера. Команда `job.resolve` сохраняет исходное окно, старые/новые значения и комментарий, затем повторно проверяет расписание. Невыполнимое закрепление блокирует активацию кандидата; действующий день остаётся прежним. Проблема на объекте (`blocked`) — отдельный сценарий.

Подход соответствует полуавтоматическому планированию: система предлагает допустимые назначения, диспетчер отвечает за согласование спорных изменений. Пример описания такого разделения: [Microsoft Field Service Schedule Assistant](https://learn.microsoft.com/en-us/dynamics365/field-service/schedule-assistant).

### Переназначение действующего плана

Обычная заявка `pending` доступна для `job.assign`: выбрать инженера либо снять закрепление. Любые последующие оптимизации соблюдают закрепление. Текущий выезд и работа не переназначаются.

`POST /api/preview` принимает действие и `expectedRevision`, создаёт кандидата на копии дня, возвращает `before/after`, полный diff и проверку закреплений. `POST /api/preview/apply` принимает `id` кандидата и `expectedRevision`; при конфликте версии, истечении кандидата или невозможном закреплении отвечает 409. Успех атомарно сохраняет JSON, повышает revision и добавляет аудит с diff. `DELETE /api/preview/:id` отменяет кандидата. Срок кандидата — 15 минут, хранение в памяти. Это защита применения кандидата, не дедупликация всех команд и не полный архив версий.

Diff содержит новые и удалённые заявки, появление/снятие назначения, смену инженера, позиции, времени, статуса и закрепления, параметры, маршруты с геометрией/сегментами, метрики и источники поездок. В UI — две карты, фильтр инженера, все строки изменений и итоговое сравнение; последний diff переживает перезапуск.

## 5. Геоданные и транспорт

Координаты зданий подготовлены через Nominatim с кэшем, ограничением 1,1 секунды между запросами и без вызовов при обычном запуске. Нераспознанные адреса имеют пустые координаты и требуют проверки. Разные номера дома нельзя молча считать одним адресом. В двух офисах исходные суффиксы «с» не совпали с найденными «к»: приблизительные точки вынесены в `data/beeline/office-assumptions.json`, отмечены в интерфейсе, доступны для изменения.

Оценочная модель остаётся доступной явно: ходьба 1,25 × расстояние / 4,8 км/ч; транспорт 1,35 × расстояние / 23 км/ч + 12 минут, выбирается более быстрый способ. В режиме `prepared` пешие поездки заменяет локальная направленная матрица дорожной сети FOSSGIS/OSM (`walking-matrices.json`), с источником, датой и идентификатором точек. Отсутствующая точка — `DATA_NOT_READY`, недоступная дуга — `null`. Общественный транспорт в этом режиме по-прежнему оценочный, без расписаний. Доступная пешая геометрия рисуется сплошной; остальные линии пунктирные.

После дополнительной проверки координаты есть у 195 из 205 заявок: 65/75/55 по участкам; 10 заявок и два офиса остаются на проверке. `geography.status=review` обозначает неполную готовность данных. Допускается частичный демонстрационный план по имеющимся точкам; он не считается полным географически подтверждённым сценарием из командного ТЗ-4. Подтверждение точки через `geography.confirm` требует источник/комментарий и обновляет все ещё не начатые визиты ровно по этому адресу, сохраняя окна. Обновление матрицы после ручного подтверждения описано в README.

Воспроизводимое сравнение на исходных участках сохраняет `npm run benchmark` в `docs/benchmark-v3.json`. В нём явно указано число геокодированных заявок и причины неназначения. Результаты разделены по двум политикам и источникам поездок; общественный транспорт оценочный, штат синтетический; это проверка прототипа, не доказательство экономического эффекта у Билайна.

## 7. Обновление сохранённого дня

Версия политики `bk-hd-v1` мигрирует ещё не начатые заявки с сохранением ID, окон, очереди и заметок; стандартные информационные визиты получают обычный приоритет и 30 минут вместо 80. Отличающаяся вручную заданная длительность сохраняется. Начатые/выполненные работы неизменны. Штат не пересоздаётся: инженеры с прежним совмещённым навыком получают явные навыки подключения и дозаказа. Перед обновлением создаётся JSON-резервная копия, изменение фиксируется в истории и diff. Для нового синтетического штата следует загрузить участок заново.
