# Допущения и границы текущего продукта «Контур»

Проверено по коду 26.09.2026. Реестр описывает реализованное поведение, включая ограничения, которые влияют на результат. Это не список обещанных доработок.

**Основные допущения:** штат и смены синтетические; время общественного транспорта оценочное; длительности работ фиксированы; планирование ведётся внутри одного дня; баланс учитывает работу на объектах; неназначенные заявки разбирает диспетчер. Отдельно выявлены расхождения с официальным PDF: четыре навыка вместо трёх, неполное разнообразие транспорта в встроенных примерах и расширенный сценарий ручного согласования окна.

| P08 | Добавление новой срочной заявки через форму включает аварийный режим.                                                                                            | **Правило продукта.** После закрытия аварии автоматического возврата в «Экономию» нет. Само редактирование обычной заявки в срочную не переключает режим; загрузка участка начинает с настроек нового сценария.                                                                                                      |
| P09 | Стабильность — мягкий штраф за смену исполнителя после более важных целей.                                                                                       | **Ограничение.** Она не фиксирует порядок и время визитов и не гарантирует минимальное число всех изменений. Ручное закрепление фиксирует инженера, но не время. Предпросмотр нельзя применить, если обязательное закрепление потерялось.                                                                            |
| P10 | Неназначенная заявка становится `manual_review`, с причиной, исходным окном и обращением диспетчеру.                                                             | **Процессное допущение.** Статус не равен отмене/отказу клиенту. Такие заявки исключены из следующего поиска, пока диспетчер явно не вернёт их через согласование. Это может удерживать заявку вне плана даже после появления свободных ресурсов.                                                                    |
| P11 | Диспетчер может вручную согласовать новое окно и вернуть заявку в планирование; комментарий обязателен.                                                          | **Расширение и расхождение с буквальным Q&A.** Автоматического сдвига нет, но Q&A запрещает сдвиг исходного окна. Функция трактуется как новое обещание клиенту по решению пользователя, а не как разрешённая оптимизатору свобода. Автоматического звонка нет.                                                      |
| P12 | При проблеме на объекте работа блокируется; затраченные время/дорога сохраняются в истории попыток. Возврат из поддержки может перепланировать её в тот же день. | **Наш сценарий.** Q&A оставляет повторные выезды и распределение на другие дни за рамками. Междневной маршрут здесь не создаётся.                                                                                                                                                                                    |
| P13 | «Удалить заявку» убирает ещё не начатую заявку из дня; перерыв/`none` моделируют недоступность инженера.                                                         | **Упрощённая модель событий.** Отдельного устойчивого статуса отмены и полноценного процесса отмены во время активного выезда нет. Удаление видно в истории изменений плана.                                                                                                                                         |
| P14 | ALNS — эвристический поиск с бюджетом; больше итераций может улучшить решение, но не гарантирует оптимум или назначение всех допустимых заявок.                  | **Ограничение.** Причина `capacity` означает «поиск не нашёл место», не математическое доказательство невозможности. Базовый алгоритм из PDF §2.3 использует исходный порядок и первого допустимого инженера с добавлением в конец.                                                                                  |
| P15 | OR-Tools подключён как наш адаптер CP-SAT с общим начальным решением и проверкой результата в JS.                                                                | **Реализация.** Это не Google Maps и не эксперимент с `RoutingModel`. Цели решаются по очереди; при лимите может фиксироваться лишь лучшее найденное значение этапа. Плохой/не найденный результат не заменяет более хороший общий начальный план. Нет общего доказательства оптимума без оптимальности всех этапов. |
| P16 | Метры в целевой функции округляются по каждому переезду; CP-SAT использует целые секунды и метры.                                                                | **Численная модель.** Времена округляются консервативно, затем маршрут проверяется в JS. Такая точность вычислений не делает входные транспортные оценки точными.                                                                                                                                                    |
| P17 | Бюджеты UI: ALNS 0–1000 итераций × 1–5 запусков; OR-Tools 1–60 секунд.                                                                                           | **Техническая граница.** По умолчанию 60 × 1 и 10 с; сохранённый день может иметь другие значения. ALNS выполняется в worker с предельным временем процесса 120 с; для Python есть отдельный тайм-аут. Это не ограничение на физическое время поездок.                                                               |
| P18 | Объяснение назначения показывает совместимость, окно, дорогу и факт смены инженера.                                                                              | **Граница объяснимости.** Полного сравнения со всеми альтернативными инженерами и доказательства «именно этот маршрут лучший» нет.                                                                                                                                                                                   |

| M01 | Для баланса трудом считается работа на объекте, включая документы; дорога, ожидание и перерыв не входят.                    | **Решение пользователя.** Это способ распределять работу, а не табель оплачиваемых часов или правовая оценка рабочего времени.                                                                                                                                                                                                                           |

| M04 | Аналитика раздельно показывает прошлое, остаток плана и весь день: работу, дорогу, ожидание, перерыв, свободное время и км. | **Определения.** Загрузка = работа / (смена − перерывы). Ожидание — после прибытия до начала клиентского окна. Свободно — остальное время смены. Интервалы ограничиваются сменой и не считаются дважды.                                                                                                                                                  |
| M05 | «Факт» работы получается из событий симуляции/ручного завершения; километры — из модели маршрута.                           | **Ограничение измерения.** Доля пройденного текущего переезда оценивается пропорционально времени. | M06 | Процент попаданий в окно считается по завершённым заявкам и фактическому началу.                                            | **Определение.** Незавершённые/неназначенные не входят в знаменатель; 100% этой метрики не означает выполнение всех заявок. Прогноз вероятности опоздания не реализован.                                                                                                                                                                                 |

Сравнение не меняет рабочий план и показывает устаревание результата при изменении дня.                                                                                                                                                       |

## Что требует явного решения перед защитой

1. **Навыки:** привести справочник к трём из PDF либо отдельно согласовать четыре. Не называть четвёртый навык улучшением соответствия ТЗ.
2. **Демонстрационные данные:** показать отдельный пример с разными транспортами, несколькими навыками инженера и непустыми требованиями оборудования; встроенные участки сами этого не покрывают.
3. **Километры:** называть оценку оценкой; даже подготовленная пешая матрица не даёт реального расчёта общественного транспорта.
4. **Согласование:** объяснять ручное новое окно как отдельное действие диспетчера; оптимизатор не изменяет обещанное клиенту время.
5. **Баланс:** заявлять учёт прошлой работы при введённой истории, а не автоматический сбор табеля или равную занятость всех сотрудников.

Аудит не менял алгоритм, справочники или сохранённый день. Связанный реестр дополнительных возможностей: [FEATURES_VS_OFFICIAL_SPEC.md](FEATURES_VS_OFFICIAL_SPEC.md).
